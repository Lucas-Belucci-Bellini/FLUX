# Data model

The schema lands in **phase 1**, alongside the first entities that must outlive
a process restart. This document describes what is already decided.

## Shape

Two kinds of table:

**Entity tables** - one per node kind (`users`, `videos`, `communities`, …),
holding the fields that belong to that thing alone: title, description, state,
counters.

**One edge table** - every relation between entities, as described in
[`../architecture/content-graph.md`](../architecture/content-graph.md):

```sql
CREATE TABLE edges (
  from_kind  text NOT NULL,
  from_id    text NOT NULL,
  edge_kind  text NOT NULL,
  to_kind    text NOT NULL,
  to_id      text NOT NULL,
  position   integer,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (from_kind, from_id, edge_kind, to_kind, to_id)
);

CREATE INDEX edges_out ON edges (from_kind, from_id, edge_kind, created_at DESC);
CREATE INDEX edges_in  ON edges (to_kind,   to_id,   edge_kind, created_at DESC);
```

The primary key makes writes idempotent. The two indexes answer the two
directions.

## Decided already

- **Identifiers are ULID-style text**, generated by the application. They sort by
  creation time, so feeds page on the primary key with no secondary sort column,
  and a client can mint an id before the row exists (optimistic UI).
- **Timestamps are `timestamptz`**, always UTC.
- **Deletion is soft where content is public.** A removed video that other rows
  point at leaves a tombstone; `detach()` clears its edges.
- **Counters are stored, not computed per read.** View and like counts are
  updated by the event pipeline; a count is never a `COUNT(*)` in a feed query.
- **Every list query is a cursor query.** No `OFFSET` in any feed path.

## Still open

- Whether comment threads use a materialised path or a parent pointer with a
  recursive query. Decided in phase 4, against a measurement.
- Whether subcommunity nesting uses `ltree` or a materialised path column.
  Decided in phase 5.
- Where counters live once they become hot. Phase 12.
